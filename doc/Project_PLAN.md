## 1. 프로젝트 개요

### 1.1 문서의 목적

본 문서는 ShareBox 프로젝트를 진행하기 위한 프로젝트 관리 계획서이다.  
프로젝트의 목표, 개발 범위, 개발 일정, 품질 관리, 산출물 관리, 위험 관리 방법을 정리하는 것을 목적으로 한다.

### 1.2 프로젝트 소개

ShareBox는 사용자가 파일을 업로드하고 공유할 수 있는 웹 기반 파일 관리 시스템이다.  
파일을 여러 저장소, 메신저, 이메일 등에 따로 보관하면 최신 파일을 찾기 어렵고, 누가 어떤 파일을 수정했는지 확인하기 어렵다.

ShareBox는 이러한 문제를 줄이기 위해 파일 업로드, 다운로드, 검색, 권한 관리, 변경 이력 관리 기능을 제공한다.

### 1.3 프로젝트 배경

문서, 이미지, 발표 자료, 설계 파일 등 다양한 파일은 여러 사람이 함께 사용하거나 수정하는 경우가 많다.  
하지만 파일을 개인별로 따로 관리하면 다음과 같은 문제가 발생할 수 있다.

1. 최신 파일과 이전 파일을 구분하기 어렵다.
2. 필요한 파일을 찾는 데 시간이 오래 걸린다.
3. 파일 수정 이력이 남지 않아 변경 내용을 확인하기 어렵다.
4. 권한 관리가 제대로 되지 않으면 불필요한 파일 접근이 발생할 수 있다.
5. 파일 공유 과정에서 중복 파일이 계속 생성될 수 있다.

따라서 본 프로젝트에서는 여러 사용자가 파일을 효율적으로 공유하고 관리할 수 있는 파일 공유 및 이력 관리 시스템을 개발하고자 한다.

### 1.4 프로젝트 목표

본 프로젝트의 목표는 사용자 간 파일 공유를 더 편리하고 안전하게 만드는 것이다.

주요 목표는 다음과 같다.

1. 파일 업로드 및 다운로드 기능 구현
2. 파일명 또는 태그 기반 검색 기능 구현
3. 파일 수정자, 수정 날짜, 변경 내용 기록 기능 구현
4. 파일별 접근 권한 관리 기능 구현
5. GitHub를 이용한 문서 및 산출물 관리

## 2. 개발 계획

### 2.1 개발 방법

본 프로젝트는 Agile Scrum 방식을 참고하여 진행한다.  
기능을 한 번에 모두 완성하기보다 파일 업로드, 다운로드, 검색, 권한 관리, 변경 이력 관리 기능을 단계별로 정리하고 구현하는 방식으로 진행한다.

Scrum 방식을 참고하는 이유는 다음과 같다.

1. 기능별로 나누어 계획하기 쉽다.
2. 진행 중 수정 사항이 생겨도 반영하기 쉽다.
3. 짧은 단위로 진행 상황을 확인할 수 있다.

## 3. 프로젝트 진행 방식

### 3.1 진행 구조

본 프로젝트는 프로젝트 수행에 필요한 작업을 단계별로 나누어 진행한다.  
계획, 요구사항 분석, 설계, 구현, 테스트, 문서화 과정을 순서대로 수행하며, 각 단계의 결과물을 확인한 후 다음 단계로 진행한다.

주요 결정 사항이나 변경 사항이 발생하면 GitHub Issue에 기록하고, 검토 후 문서와 산출물에 반영한다.

### 3.2 의사소통 방법

| 방식 | 목적 |
|---|---|
| GitHub Issue | 수정 요청, 리뷰 의견, 오류 내용 기록 |
| Pull Request | 문서 또는 코드 변경 사항 확인 |
| 메신저 | 간단한 질문 및 진행 상황 공유 |
| 회의 | 주요 결정 사항 논의 및 일정 조정 |

## 4. 품질 관리 계획

### 4.1 품질 목표

| 항목 | 목표 |
|---|---|
| 기능성 | 주요 기능이 정상적으로 동작해야 한다. |
| 사용성 | 사용자가 쉽게 파일을 업로드하고 찾을 수 있어야 한다. |
| 보안성 | 권한이 없는 사용자는 파일에 접근할 수 없어야 한다. |
| 신뢰성 | 파일 정보와 변경 이력이 누락되지 않아야 한다. |
| 유지보수성 | 기능별로 내용을 구분하여 수정하기 쉽게 관리한다. |

### 4.2 품질 관리 방법

1. 기능 구현 후 기능별 테스트를 수행한다.
2. 오류가 발견되면 GitHub Issue에 기록한다.
3. 주요 문서는 리뷰를 거쳐 수정한다.
4. 수정 사항은 GitHub commit으로 기록한다.
5. 최종 제출 전 산출물 목록을 기준으로 누락 여부를 확인한다.

### 4.3 테스트 계획

| 파일 다운로드 테스트 | 업로드된 파일을 정상적으로 다운로드할 수 있는지 확인한다. |
| 파일 검색 테스트 | 파일명 또는 태그로 검색 결과가 나오는지 확인한다. |

```text

```

예시:

```text

```

## 8. 리뷰 및 수정 계획

작성한 프로젝트 관리 계획서는 GitHub에 업로드한 뒤 리뷰를 요청한다.  
리뷰는 GitHub Issue 또는 Pull Request 댓글을 통해 진행한다.

리뷰 요청 시 다음 항목을 중심으로 검토를 요청한다.

1. 프로젝트 목표가 명확한지
2. 개발 범위가 적절한지
3. 주요 기능이 프로젝트 목적에 맞는지
4. 일정 계획이 현실적인지
5. 리스크 관리 내용이 충분한지

리뷰 내용 중 타당한 의견은 문서에 반영하고, 수정 내역은 commit으로 기록한다.

예시 commit 메시지:

```text
docs: 리뷰 의견 반영하여 프로젝트 관리 계획서 수정
```

본 프로젝트는 다음 조건을 만족하면 완료된 것으로 본다.

1. 프로젝트 관리 계획서가 GitHub에 업로드되어 있다.
2. README에 프로젝트 문서 링크가 정리되어 있다.
3. 주요 기능과 요구사항이 문서에 정리되어 있다.
4. WBS와 개발 일정이 작성되어 있다.
5. 품질 관리와 리스크 관리 계획이 포함되어 있다.
6. 리뷰를 받고 수정 사항을 반영하였다.
